### 1. 이번 주차 새로운 시도: 코드 리뷰 받기 좋은 코드 구조 설계
이번 주차에는 **코드 리뷰 받기 좋은 코드 구조를 설계해보자**를 새로운 시도로 삼았습니다.  
원래는 Stream API를 학습하고 적용해보려 했지만, 일반적인 구현에서도 충분히 대체 가능하다고 판단해 우선순위를 낮췄습니다.  
대신, 이전 주차의 미션 수행과 코드 리뷰 경험을 바탕으로 **좋은 구조와 객체지향적 설계란 무엇인지**를 고민했습니다.

리뷰를 주고받으며 특히 느낀 점은, 제가 아무리 자세히 설명을 덧붙여도 **코드 구조 자체가 직관적이지 않으면 리뷰어가 이해하기 어렵다**는 것이었습니다.  
즉, 좋은 코드란 단순히 기능이 동작하는 것을 넘어, **누군가가 쉽게 읽고 이해할 수 있어야** 하고, 그 과정에서 **테스트 용이성, 가독성, 객체지향 원칙의 적용**이 자연스럽게 드러나야 한다는 결론에 도달했습니다.

또한 제가 이전에 사용하던 구조는 잘 알려진 디자인 패턴이 아니어서, 별도의 설명 없이 리뷰어에게 전달되기 어렵다는 점도 체감했습니다.  
실제로 리뷰를 요청했지만 피드백을 받지 못한 경험도 여러 번 있었기 때문에, 이번에는 **누가 봐도 직관적으로 이해할 수 있는 구조**를 만드는 데 초점을 맞추게 되었습니다.  

이러한 고민을 바탕으로 코드를 구조화하다 보니, 자연스럽게 **MVC와 유사한 형태로 귀결**되었습니다.  
애초에 MVC를 목표로 한 것은 아니었지만, **역할을 명확히 분리하려는 시도**를 하다 보니 입출력 로직, 핵심 도메인 로직, 제어 흐름이 각각 독립적인 영역으로 나뉘게 되었습니다.

물론 이번 애플리케이션은 뷰가 단일 콘솔 인터페이스로 구성되어 있어 엄밀한 의미의 MVC 패턴이라고 보긴 어렵습니다.  
하지만 **보기 좋고 이해하기 쉬우며 잘 알려진 구조**라는 관점에서, 그리고 **코드 리뷰 시 맥락이 명확히 전달되는 구조**라는 점에서 MVC와 유사한 형태가 가장 적절하다고 판단했습니다.

다만 MVC 적용에만 집중한 것은 아닙니다.  
메서드를 15줄 이내로 유지하며 기능을 세분화했고, 일급 컬렉션을 활용해 **검증과 관련 로직을 객체 내부로 자연스럽게 이동**시켰습니다.  
또한 변수명과 메서드명을 직관적으로 작성하려고 해서 코드의 의도가 최대한 드러나도록 노력했습니다.

이번 시도를 통해 단순히 “패턴을 적용했다”는 수준을 넘어,  
**코드 리뷰를 염두에 둔 구조는 명확한 역할 분리와 읽기 쉬운 코드에서 비롯된다**는 점을 다시 한번 생각하게 되었습니다.

### 2. 코드 리뷰 피드백 반영
1주차 코드 리뷰에서 받은 피드백을 최대한 반영했습니다.
- 메서드를 15줄 이내로 세분화하여 가독성과 유지보수성을 개선했습니다.
- 클래스와 메서드 역할을 명확히 나누어 책임을 분리했습니다.
- 일급 컬렉션을 도입하여 객체 생성 시 검증과 관련 로직을 자연스럽게 처리하도록 설계했습니다.

다른 사람의 코드를 리뷰하면서 메서드 분리와 클래스 설계 방식에서 많은 인사이트를 얻었고, 이를 기억해 두었다가 이번 프로젝트에 적용했습니다. 결과적으로 코드가 훨씬 깔끔하고 객체지향적이라는 체감을 할 수 있었습니다.

### 3. 자체 목표: 생성형 AI 최소화( [러다이트단 챌린지에 참여한 이유](https://blog.naver.com/gyhukyh011/224056632287))
이번 프로젝트에서도 설계, 구현, 테스트, 디버깅, 1차 리팩토링까지 생성형 AI 사용을 최소화했습니다.  
직접 구현하고 문제를 해결하며 얻은 경험은 오래 기억에 남았고, missions-utils 라이브러리까지 직접 확인하며 학습한 경험은 단순 AI 활용보다 훨씬 깊이 있는 학습으로 이어졌습니다.

### 4. 설계의 중요성
이전 미션 수행 시 완벽하지 않은 설계로 인해 작업 시간이 지연된 경험을 바탕으로, 이번 프로젝트에서는 **큰 그림 위주의 설계**에 집중했습니다.
- 메서드명, 리턴 타입 등 세부 구현은 기능 구현 중 변경될 수 있음을 인지하고, 먼저 구조와 역할을 분할하는 데 초점을 맞췄습니다.
- 큰 그림을 잡은 후 작은 기능부터 점진적으로 구현하면서 설계와 구현이 조화를 이루도록 노력했습니다.

### 5. 테스트 경험과 설계
이전 주차 미션에서 TDD를 시도했지만, 유닛 테스트와 JUnit, assertJ 경험 부족으로 **테스트를 위한 코드에 매몰**된 경험이 있었습니다.  
이번 주차에서는 TDD를 적용하지 않고, 테스트 라이브러리와 유닛 테스트에 익숙해지는 데 집중했습니다.
- 테스트만을 위한 설계가 아닌, 기능 구현에 적합한 설계를 목표로 하였습니다.
- 자연스럽게 테스트하기 좋은 코드가 작성되었고, 실제로 테스트 코드에서 버그를 발견하며 테스트의 효율성을 체감했습니다.
- 특히 랜덤 숫자 생성 기능을 테스트할 때, 라이브러리에서 랜덤 기능을 배제하고 예측 가능한 값으로 테스트함으로써 실제로 테스트하기 어려운 기능도 검증할 수 있음을 경험했습니다.

### 예외 테스트 통과 실패 문제와 원인 분석
- **문제 상황**  
  `ApplicationTest`의 예외 테스트가 통과하지 않음.  
  예외 메시지에 `[ERROR]`를 포함하고 `IllegalArgumentException`을 던졌음에도 실패.

- **원인 파악 과정**  
  `NsTest`에서 `System.out`을 `ByteArrayOutputStream`으로 캡처하고 있었는데,  
  나는 예외를 `throw`만 했을 뿐 **출력은 따로 하지 않았음**.  
  예외 발생 시 출력도 요구사항에 포함되어 있음을 뒤늦게 확인.

  출력 코드를 추가했지만 여전히 실패 → 원인을 재검토한 결과,  
  **입력 검증 실패 시 재입력을 받도록 해야 하는 로직**이 누락되어 있었음을 발견.

- **결과**  
  단순히 예외 메시지 일치뿐 아니라 **입력 흐름 전체를 테스트가 검증하고 있음을 인지**해야 했음.  
  테스트 통과를 위해서는 “출력 + 재입력 루프”까지 구현되어야 함을 깨달음.

### 일급 컬렉션(First-Class Collection)의 도입
- **도입 배경**  
  이전 미션 리뷰에서 일급 컬렉션을 권장받았으나 개념 이해 부족으로 미도입.  
  이후 다른 사람의 과제 코드를 리뷰하면서,  
  **일급 컬렉션을 통해 검증 및 관련 로직을 객체 내부로 이동시키면 코드가 훨씬 깔끔해짐**을 실감.

- **적용 과정**  
  이번 로또 미션에서 `Lotto` 클래스가 일급 컬렉션 구조임을 확인 후 적극 활용.  
  `Lotto` 객체 내에 검증 로직과 관련 메서드를 포함시켜 응집도를 높임.  
  당첨 번호, 보너스 번호 등도 동일한 방식으로 관리하도록 구조 개선.

- **효과**  
  도메인 객체 중심의 설계로 전반적인 **책임 분리와 코드 가독성** 향상.

---

### 당첨 통계 자료 구조 선택: Map vs 배열/리스트
- **고민 포인트**  
  당첨 통계를 어떤 자료구조로 관리할지 고민.  
  배열은 직관적이며 메모리 효율적이지만, **확장성과 유연성에 제약**이 존재.  
  리스트는 배열보다 유연하지만 본질적으로 큰 차이는 없음.

- **결정 이유**  
  등수나 조건이 늘어나거나 변경될 가능성을 고려하면,  
  **Map을 사용하는 것이 확장성과 유지보수성 측면에서 유리**하다고 판단.  
  성능상 손해보다 구조적 유연성이 더 중요하다고 봄.

- **결과**  
  `Map<Rank, Integer>` 형태로 통계 관리하여 등수별 결과 집계.

---

### 상수 및 메시지 관리 전략
- **에러 메시지 관리**  
  각 클래스에서 따로 관리할 수도 있었지만,  
  **입력 검증 외의 에러 메시지도 존재**할 수 있기 때문에 중앙화된 관리 방식이 적합하다고 판단.  
  → `ErrorMessage` 클래스로 일원화.

- **로또 공용 상수 관리**  
  공용 상수가 많지 않아 `enum`보다는 **단순 상수 클래스**로 관리.  
  `enum`으로 관리할 경우 오히려 코드 복잡도만 증가한다고 판단.

- **입출력 메시지 관리**  
  초기에는 `InputMessage`, `OutputMessage` 클래스로 분리하려 했으나,  
  실제로는 해당 View 클래스 외에서는 사용되지 않음.  
  불필요한 추상화를 피하고 **각 View 클래스 내부 상수로 한정**함.

---

### 서비스 계층의 로또 리스트 관리 여부
- **초기 설계**  
  MVC 패턴을 적용하면서 `Service` 계층에 로또 리스트를 저장하고 통계 기능을 함께 처리.  
  그러나 실제 로직을 살펴보니 컨트롤러 대비 **서비스 계층의 역할이 모호함**을 느낌.

- **재검토 결과**  
  서비스가 데이터를 ‘보관’하는 구조는 **확장성과 책임 분리 측면에서 부적절**함.
    - 서비스는 비즈니스 로직 중심으로 동작해야 하며,  
      데이터 상태는 도메인 또는 외부 저장소에서 관리하는 것이 원칙.
    - 현재는 단순한 콘솔 프로그램이라도,  
      이후 외부 저장소나 다른 입력 채널이 생기면 구조가 쉽게 깨질 위험이 있음.

- **결론**  
  서비스는 로또 생성 및 통계 계산 로직만 담당하고,  
  로또 리스트의 관리 책임은 **도메인 객체나 컨트롤러 흐름 내에서 처리**하도록 개선.

---

### private 메서드의 테스트 여부

- **문제 의식**  
  요구사항에서 클래스와 메서드별 테스트를 작성해야 했으나,  
  메서드당 15줄 제한으로 인해 기능을 세분화하면서 **클래스 내부에서만 사용하는 private 메서드**가 다수 생김.  
  이에 따라 이러한 private 메서드를 **별도로 테스트해야 하는가**에 대한 의문이 생김.

- **고민 및 판단**  
  private 메서드는 외부에서 직접 호출되지 않고,  
  같은 클래스의 공개(public) 메서드를 보조하는 내부 로직 역할을 함.  
  따라서 public 메서드를 테스트하는 과정에서 이미 해당 private 메서드의 동작도 함께 검증된다고 판단함.  
  즉, **private 메서드를 직접 테스트할 필요는 없으며**,  
  오히려 클래스 내부 구현 세부사항에 대한 과도한 결합을 초래할 수 있음.

- **결론**  
  private 메서드는 직접 테스트하지 않고,  
  이를 사용하는 public 메서드의 테스트를 통해 간접적으로 검증하는 것이 바람직하다고 결론지음.

<summary><b>Lotto Application 구조</b></summary>

#### Application

* 프로그램 진입점
* 전체 실행 흐름 관리

#### InputView

* 사용자 입력 및 안내 담당

    * 구입 금액 입력 및 검증
    * 당첨 번호 입력

* 로또 한 장 객체

    * 번호 범위(1~45) 검증
    * 6개 숫자, 중복 없음 검증
    * 생성자에서 검증 수행
    * 로또 번호 조회 기능 제공

#### LottoController

* 로또 로직, View, Service 연결
* 입력 → 로또 생성 → 결과 출력 흐름 제어

#### LottoService

* 핵심 비즈니스 로직 담당

    * 로또 생성
    * 당첨 번호와의 일치 여부 계산
    * 통계 및 결과 생성

#### WinningNumbers

* 당첨 번호 객체

    * 번호 6개, 중복 없음, 범위(1~45) 검증
    * 보너스 번호 1개, 중복 없음, 범위(1~45) 검증
    * `Lotto` 객체 활용
    * 일치 여부 확인 기능 포함

#### PurchaseAmount

* 구입 금액 관리

    * 숫자인지 검증
    * 1,000원 단위 검증
    * 구매 가능한 로또 장 수 계산

#### BonusNumber

* 보너스 번호 관리

    * 숫자 여부 검증
    * 1~45 범위 검증
    * 당첨 번호와 중복되지 않는지 검증

#### PrizeStatistics

* 당첨 통계 관리

    * 총 상금 계산
    * 수익률 계산 (총 상금 / 구입 금액 × 100)

#### Prize (Enum)

* 등수별 정보 관리

    * 일치 숫자 개수
    * 보너스 포함 여부
    * 상금 금액

#### OutputView

* 출력 담당

    * 구매 내역 출력
    * 당첨 통계 출력
    * 수익률 출력
</details>
